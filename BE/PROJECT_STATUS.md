## 2. Chạy dự án

```bash
cd BE && source .venv/bin/activate          # venv có sẵn: BE/.venv (Python 3.14 local, Dockerfile dùng 3.11)
python -m uvicorn app.main:app --reload --port 8000        # PHẢI chạy trong thư mục BE (không phải thư mục gốc repo)
python -m pytest -q                         # chạy trên DB trong BE/.env (Supabase thật). Toàn bộ suite ~70 phút (Codespace tự tắt sau 30 phút im lặng); nhanh hơn: Postgres Docker cục bộ `vhrs-testdb`, ~3 phút (DATABASE_URL trỏ vào đó); KHÔNG chạy hai phiên pytest cùng lúc
python scripts/seed_workshop_data.py --dry-run             # xem seed sẽ ghi gì; bỏ --dry-run để ghi (idempotent)
```
`BE/.env` (đã `.gitignore`, **không bao giờ in/commit**): `DATABASE_URL` (Supabase session pooler), `JWT_SECRET`, `SUPABASE_URL`,
`SUPABASE_SERVICE_KEY`, `STORAGE_BUCKET=order-inputs`. Thiếu `.env` → hỏi chủ dự án, không giả lập. Swagger: `/docs`.
Tài khoản demo trên Supabase: `customer@example.com`, `khach@example.com`, `staff@netviet.vn`, `manager@netviet.vn`, `tech@netviet.vn`, `admin@netviet.vn`
(mật khẩu do chủ dự án giữ; **đổi trước khi deploy công khai**).

### Script database để nộp (`database/AI-VHRS_database_full.sql`) — QUY TẮC BẮT BUỘC

`BE/database/AI-VHRS_database_full.sql` là **một file SQL duy nhất tạo toàn bộ database** (schema của baseline và của mọi migration, row-level security, trigger, hàm, dữ liệu tham chiếu: 5 vai trò, tài khoản demo, bảng giá đầu, loại bút, tham số hệ thống) để chủ dự án nộp. Hiện ở revision **0011** (đã nạp sạch vào DB trống, khớp Supabase về cột và chỉ mục). **Mỗi khi có thay đổi database (migration mới, sửa trigger/hàm/ràng buộc/chỉ mục, thêm dữ liệu tham chiếu), AI PHẢI tạo lại file này trong cùng lượt làm việc và nhắc chủ dự án commit nó:**

```
cd BE && source .venv/bin/activate
docker start vhrs-testdb                       # Postgres cục bộ (cổng 55432); đưa nó lên head: alembic upgrade head với DATABASE_URL trỏ vào đó
.venv/bin/python scripts/build_database_script.py     # kiểm tra DB nguồn đang ở revision head rồi ghi lại file
```
Cách kiểm chứng đã dùng (làm lại mỗi lần): nạp file vào một database trống (`psql -v ON_ERROR_STOP=1 -f ...`) rồi so cột, chỉ mục, enum, trigger, hàm, tên ràng buộc với DB nguồn (đều khớp ngày 2026-10-22; Supabase thật cũng khớp ở mọi hạng mục). Chủ dự án đã **uỷ quyền (2026-10-22): khi một việc đã được duyệt cần đổi database, AI tự chạy migration lên Supabase** (phải kiểm tra trước/sau, ghi vào mục 7 và changelog, báo lại); việc **xoá/đổi dữ liệu thật** vẫn phải hỏi.

## 4. Bản đồ code (`BE/app`)

```
api/v1/*        route mỏng: auth, me, catalog, pricing, orders, customer_quotes, messages, payments,
                workshop (Staff+Manager), manager (phân công, duyệt giá), manager_ops (vật tư/giá/robot), scheduling (+ nhật ký job, sự cố),

api/*schemas.py Pydantic in/out (tách khỏi ORM): schemas, order_schemas, staff_schemas, ops_schemas, photo_schemas, delivery_schemas
services/       nghiệp vụ: orders, pricing(thuần), quotations, payments, manager_catalog, scheduling, staff_orders, sketches,
                messages, notifications(hook, chưa gửi), audit, workshop_access(phân quyền bản ghi), technician (vòng đời job),
                product_photos (ảnh + QC, nộp ảnh, QC fail), acceptance (nghiệm thu, viết lại, tự nghiệm thu), delivery (chọn cách nhận, thanh toán cuối, bàn giao tại xưởng), stroke_ai/ (AI thật)
domain/         luật thuần (không DB): carrier_rules (máy trạng thái vận đơn, ánh xạ trạng thái GHN, kiện hàng), quotation_rules, payment_rules, pricing_config_rules, scheduling_rules, job_rules, photo_rules (ảnh/QC/nghiệm thu), delivery_rules (gói, phí, số tiền cuối, địa chỉ, khung giờ nhận)
repositories/   truy cập dữ liệu (không nghiệp vụ): accounts, catalog, orders, workshop, ops
models/         ORM ánh xạ bảng có sẵn: account, catalog, order, sketch, ops   (schema do SQL migration sở hữu)
integrations/   storage (Supabase Storage + InMemoryStorage cho test), payment_gateway (MOCK + bộ chọn adapter thật), vnpay, momo,
                carrier (port + MockCarrier + bộ chọn), ghn (hãng duy nhất), locations (danh mục tỉnh/phường + cache), mailer (console)

scripts/seed_workshop_data.py   seed dữ liệu thật lên Supabase (idempotent)
tests/          conftest.py (dọn dữ liệu tiền tố pytest_) + test_* (xem mục 6)
```
Luồng một request: `api` → `services` → `repositories` → `models`. **Trạng thái đơn do trigger DB `fn_order_state_guard` quyết định**
(service chỉ UPDATE; sai → lỗi `P0409` → HTTP 409 `STATE_CONFLICT`); không nhân đôi luật chuyển trạng thái ở Python.
Trạng thái báo giá/job **không** có trigger: do service kiểm tra (job: `domain/job_rules.py`; mỗi bước job đổi kèm `production_status` của đơn trong cùng giao dịch, BR-17).

## 5. Quyết định kiến trúc đã chốt (không đổi nếu chưa hỏi chủ dự án)

- Python 3.11 (3.14 local) · FastAPI · SQLAlchemy 2 · Alembic · PostgreSQL (Supabase) · Pydantic v2 · JWT + session server-side · httpx · OpenCV headless · Hershey-Fonts · fpdf2.
- Lỗi: `{"error":{"code","message","details"}}`; phân trang `{items,total,page,page_size}`.
- Phân quyền bản ghi: đơn của người khác → **404**; sai vai trò → **403**. Staff thấy đơn được giao + pool `SUBMITTED` chưa ai nhận (chỉ đọc tới khi nhận); Manager thấy mọi đơn không phải `DRAFT`.
- **Manager không xử lý đơn như Staff** (chủ dự án chọn 2026-10-17): Manager chỉ **đọc** mọi đơn, phân công Staff, duyệt/từ chối giá vượt ngưỡng, quản vật tư/mẫu chữ/robot/bảng giá/ngưỡng %, lập lịch; mọi lệnh ghi trong `/workshop/*` (accept, reject, phác thảo, báo giá, điều chỉnh, gửi) là **STAFF only**; Manager **được** nhắn tin với khách trong chat để xử lý khiếu nại; Manager không tự duyệt giá của chính mình. Ma trận quyền toàn API được test tự động ở `tests/test_permission_matrix.py`.
